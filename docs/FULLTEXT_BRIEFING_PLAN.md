# 全文阅读与十条每日简报修改方案

日期：2026年11月5日。2026年11月6日用户已确认默认5加5、内容不足允许少报，并授权实施与本地真实Markdown展示。状态：本地实现与真实Markdown展示完成，线上投递与跨天验收待完成；基于已发布的v0.3.0实现0.4版本，本轮不发布新版本或发送飞书。

目标是每天替用户阅读原文，选出值得关注的10条信息，生成可直接阅读的中文简报并推送飞书。部署继续使用GitHub Actions，程序一次执行后退出。

## 当前问题与修改目标

| 当前情况 | 对用户的影响 | 修改目标 |
| --- | --- | --- |
| 默认读取RSS、HN、TLDR提供的标题及摘要 | 无法覆盖正文中的条件、限制和实际用法 | 为入选内容取得可用正文，模型处理正文后再生成摘要 |
| generate.py只传摘要前300字符 | 即使来源材料较丰富，模型也看不到完整内容 | 摘要仅用于初筛；正文按实际输入预算完整处理 |
| 默认目标5条，配置最多8条，板块各最多3条 | 无法配置一份10条简报 | 默认10条，默认行业热点5条、产品案例5条 |
| 候选在排序及编排中被截断为20条 | 可能在语义判断前丢掉用户关心的内容 | 移除默认链路固定20条限制，按来源范围、输入预算和执行时间分批处理 |
| 没有独立的用户偏好评分 | 用户难以说明什么值得看、为什么入选 | 可编辑兴趣画像、明确评分标准、保留选中与排除理由 |
| URL去重不能识别同事件的不同报道 | 一份简报可能被同一事件占据 | 结合链接、正文和事件语义去重，并在最终选稿时复核 |
| 主要记录来源和投递状态 | 很难知道模型实际读了什么 | 增加正文获取、模型输入覆盖、选稿与用量记录 |

已有的CLI、单次进程、来源适配器、SQLite、投递幂等、状态退出码和Actions部署继续复用。旧Web与agent.py保留，不重写整个项目。

## 借鉴 AI News Scanner 的内容

[AI News Scanner](https://github.com/backpropagation6/ai-news-scanner)提供了容易理解的初筛方式：在配置里描述用户身份、关注内容和高低分例子，模型逐篇返回评分、理由和标签，再由程序过滤。

本项目采用这种偏好表达方式，并将综合分拆为可解释的维度。该项目自身只向模型发送短摘要，不具备全文阅读、固定十条或整份简报多样性选稿，因此只作为初筛设计参考。

保留本项目现有的失败语义与密钥约束。不会照搬其他项目的静默异常、部署组件或固定评分门槛。

## 用户收到的简报

默认一份10条，行业热点和产品案例各5条。沿用80至140字中文摘要、简短关注理由和原文链接，以约3至5分钟的阅读负担为目标，后续按实际样稿调整。全文阅读的价值体现在信息准确和取舍，不通过堆长摘要体现。

每条摘要应交代发生的变化、实际意义，以及正文中影响判断的条件或限制。产品案例额外突出目标人群、问题、用法和新意。宣传、作者主张和社区估计按其性质表述，不能改写成已经独立验证的事实。

正文获取成功与事实可信程度分别表示。来源可标记为官方发布、媒体报道或社区自述，不再仅因来源名称包含“官方”就把陈述写成独立确认的事实。

卡片底部同时显示来源覆盖与正文阅读结果。例如“本期10条均依据取得的正文生成；候选中2篇正文不可用，已递补”。详细选稿理由、评分和错误放在运行记录中，不把调试信息塞进卡片正文。

10条是交付目标。候补耗尽、正文不可用或合格内容不足时，明确少报并返回降级状态，不用摘要片段冒充全文、不编造条目，也不擅自跨出配置的时间范围。默认不跨板块补位。

显式配置为5条的旧配置仍可运行；配额根据目标数量与启用板块计算，替换当前分散的硬编码数字。历史简报不改写。

## 新的执行流程

```text
读取配置与兴趣画像
→ 多来源发现文章
→ 链接去重、时间过滤和明显无关内容初筛
→ LLM依据来源摘要判断阅读优先级
→ 形成候选队列与候补队列
→ 按优先级获取、清洗并保存正文
→ 模型依据正文复核价值、生成单篇摘要
→ 合并重复事件，按板块和多样性选出10条
→ 校验内容与证据
→ 保存简报、推送飞书、退出
```

摘要初筛不锁死最终10篇。正文获取失败、内容与标题不符、重复或实际价值不足时，从候补递补，直到达到配额、候补用尽或本轮预算耗尽。

不再把一次模型请求作为产品硬限制。初筛可批量处理；正文通常按文章处理，超长文章分段；最终组合选稿按需要比较已读文章。每次请求的输入量和整轮执行时间仍受明确预算约束，触及预算必须说明，不能悄悄截掉正文后宣称读完。

## 初筛与选稿标准

### 兴趣画像

借鉴AI News Scanner，在pulse.yaml增加selection配置。用户只需先描述关注和排除内容；权重属于进阶配置。

```yaml
selection:
  profile: |
    我关注AI前沿变化，以及能带来开发与产品灵感的真实案例。
    高优先级：模型与工具的实质变化、具体应用场景、可复现实践。
    低优先级：纯融资、人事变动、广告、缺少实际差异的套壳。
    也希望发现未主动关注过、但与AI开发相关的新思路。
  weights:
    relevance: 1
    impact: 1
    usefulness: 1
    novelty: 1

output:
  items: 10
  max_items: 10
```

以上等权是可比较的初始基线，不是经过实验得出的最优权重。先通过样本验证标准，再决定是否提高某个维度；不预设没有依据的35%、20%等精细比例。

### 结构化判断

| 维度 | 主要判断 |
| --- | --- |
| relevance 相关性 | 是否符合用户关注的AI开发、动态与应用灵感 |
| impact 影响 | 是否改变能力、成本、部署方式或开发决策 |
| usefulness 实用与启发 | 是否有具体人群、使用流程、案例或可执行线索 |
| novelty 信息增量 | 是否提供新进展，而非重复已知内容 |

每项使用0至3的粗分档：0不满足、1较弱、2明确、3较强，并用提示词中的具体例子校准。LLM返回各维度分数、理由、材料依据、板块、主题，以及需要补充阅读的标记。程序计算加权分，便于解释和重放。

排除规则优先于分数；高热度不能抵消明确不感兴趣或与历史重复的问题。融资新闻若包含独立、实质的产品发布，应判断主体内容，避免关键词一刀切。

初筛时缺少摘要的HN条目不按“低质量”直接淘汰；区分材料不足与价值低，必要时进入补充阅读队列。初筛不能声称已经验证文章事实，正文阶段再复核。

### 不同来源的处理

文章价值使用统一维度；来源特有的信号分开处理。HN热度仅作源内辅助信号，不与无点赞数据的RSS直接比较；没有热度数据不计为0分惩罚。官方发布有一手材料价值，但宣传主张仍需保留出处与限制。

RSS、TLDR、媒体可能都指向同一事件。初筛识别候选重复，正文阶段确认是否只是转载，或确有独立新增信息。来源覆盖与独立证据数量分别记录，转载次数不能冒充交叉验证。

已推送历史提供最近去重窗口的标题、摘要和事件信息供比较；不再只取固定20条历史记录。稳定URL原文更新检测不在本轮承诺范围内，保留现有链接去重窗口。

### 最终十条的组合

分别在行业热点与产品案例中排序，再处理同事件重复、主题过度集中和重要内容遗漏。多样性作为相关内容之间的重排因素，不为凑来源数量保留明显低价值文章。

采用“相关且提供新增信息”的选稿原则，参考[MMR的重排思路](https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf)。初版使用主题、实体和事件判断，不引入向量数据库或训练推荐模型。排序参数和候补规模随样本结果调整，不重新宣布一个固定候选数最优。

## 正文获取与模型阅读

### 第一版支持范围

优先支持公开静态HTML正文、RSS或Atom明确提供的文章正文、HN原生长帖，以及GitHub项目README。项目README应标记为项目说明，不宣称已经阅读仓库全部代码。

网页正文提取优先评估[Trafilatura](https://trafilatura.readthedocs.io/en/latest/)，只负责解析已经通过现有Network取得的HTML。网络生命周期、公开地址校验、重定向和超时继续复用，避免另起一套下载逻辑。以真实样本验证效果后再加入运行依赖。

PDF、登录页面、付费墙和必须运行浏览器脚本才能显示的正文，首版标记为不支持或不可用并递补，不引入常驻浏览器或付费抓取平台。

### 来源与原文的关系

同时保存发现地址、最终访问地址，以及明确识别出的原文地址。TLDR已经给出原文链接时直接阅读目标文章。对已知聚合摘编页面，有明确“阅读原文”链接时追溯上游；不遍历页面中的所有外链。

仅取得聚合站摘编、登录提示或短预览时，不计为严格全文阅读成功。无法取得上游内容则记录secondary_only或unavailable并递补。ai-pulse-lab.com/feed.xml可作为这种情况的测试样本，不因采用RSS协议就视为全文来源或自动加入默认源。

### 完整处理正文

取得正文后保存文本与来源、时间、内容哈希。按段落处理并保留标题、列表和代码等与理解有关的结构；不再按300字符截断。

能在预算内处理的文章，整篇交给模型；超长文章按段落切分，每段均经过模型处理，再依据带出处的结果合成单篇摘要。记录分段范围及是否覆盖全部提取正文，不把只读开头标成已读全文。这里的完整覆盖指模型输入覆盖已取得的正文，不保证网页提取器能发现付费或动态隐藏内容。

模型返回关键事实依据，引用必须能对应保存的正文片段。证据ID存在不等于陈述已经被证实；确定性检查可覆盖片段是否存在、数字与单位是否对应、引用是否越界，最终准确性仍通过样本人工复核。

## 数据保存与可见失败

在现有SQLite上增量增加正文和评估记录，不删除原表。正文记录关联entry_id，保存最终URL、提取方式、状态、正文、内容哈希、时间及错误；评估记录关联run_id和entry_id，保存初筛分数、理由、阅读覆盖、正文复核和排除原因。

正文状态至少区分ready、insufficient、secondary_only、unavailable和unsupported；模型输入覆盖另记complete、chunked_complete、partial或not_read。两个状态不能混成一个“成功”。摘要、正文和最终中文摘要使用独立字段，避免继续复用summary造成含义混淆。

运行记录提供各阶段数量：发现、规则排除、初筛、尝试阅读、正文就绪、全文处理完成、复核淘汰、递补和最终入选。模型用量分阶段记录，保留实际输入、输出、调用次数和耗时；服务商没有返回的用量保持未知。

| 情况 | 处理 |
| --- | --- |
| 全部来源失败，或没有可用正文与合格内容 | failed，退出4 |
| 模型整体不可用、数据库或程序错误 | failed，退出3 |
| 部分来源失败，或合格内容不足目标数量 | partial或degraded，退出1 |
| 某篇正文失败，但递补后完整交付目标数量 | 可成功，逐篇失败、递补及覆盖结果仍必须可见 |
| 简报存库但全部投递失败 | degraded，退出1，保留投递重试 |
| 来源、完整阅读与目标数量满足要求，投递正常 | success，退出0 |

独立文章失败可以继续处理候补；不能把模型批次失败静默转成“没有相关新闻”，也不能对空正文调用模型后伪装为全文总结。

本地正文保存在忽略的数据目录。Actions作业中也保存正文用于处理和追溯，但默认上传的状态制品需排除原文与私人邮件正文，仅保留恢复去重、选稿和投递所需的状态与有限证据。增加一致的状态快照导出步骤，避免直接把新增正文表随整个数据库公开分发。Actions作业结束后不默认长期归档全文；长期全文归档作为后续独立选项。

## 分阶段实施与验收

### 阶段一 正文获取和存储

先完成内容模型、正文读取、增量迁移及不含原文的状态快照。用公开静态HTML、RSS全文、聚合摘要、空正文、HTTP错误和项目README样本验证。正文不能取得时状态明确，重跑不会破坏旧数据库或投递记录。

### 阶段二 基于正文生成摘要

打通“已取得正文 → 模型输入 → 摘要与证据”的独立路径。测试把关键限制放在原文后半段，断言它实际进入模型输入；验证长文各段均被处理、非法引用拒绝、生成失败可见。通过后再接初筛，避免先写复杂排序却没有正文能力。

### 阶段三 偏好初筛和十条选稿

接入兴趣画像、分档评分、队列、全文复核、事件合并和递补。使用足够多的不同事件样本，验证默认5加5、材料不足不凑数、跨来源同事件只占一个位置、短摘要条目可进入补读、预算耗尽说明，以及已发送内容不重复。

### 阶段四 简报输出与实际评价

验证10条Markdown和飞书payload，单次发送仍满足大小限制；已有成功sink不会在重试时再次发送。完整pytest、Ruff、Python3.11和3.12 CI及安装包的离线命令必须通过，不以删测试或放宽正文要求实现通过。

真实评价使用同一批文章，比较“直接按摘要选稿”和“偏好初筛加全文复核”，由用户标记必看、可看、不看及原因。关注最终10条的有用程度、重复、事实或限制遗漏，并抽检未入选文章。记录实际请求数、token和耗时后调整权重与候补预算，不在测试前承诺成本或速度改善。

真实模型测试应控制样本规模并记录用量；Webhook准备好后再进行首次真实飞书投递和连续三天Actions验收。全套真实联调不由离线测试替代。

## 本轮保留的边界与待确认默认值

本轮聚焦全文阅读、偏好初筛和10条简报；信息源勾选界面、任意网页自动适配、PDF阅读、浏览器自动化采集和长期全文归档后置。现有来源仍需实际验证供给量，不能保证三个默认来源每天都有10个合格事件；不足时明确说明，再决定补充哪些来源。

等待确认的默认方案为：10条，行业与产品各5条；必须具备可用正文并经过模型完整处理；不足时递补并如实少报；初筛采用用户画像及四维等权基线；正常流程允许多次模型请求；先实现公开网页与已有来源，不扩大部署架构。

用户确认后，再按上述阶段修改代码，并更新与本轮明确目标冲突的旧规格和AGENTS说明。v0.3.0标签保持不动，新能力完成验收后单独确定下一版发布与推送，不在方案阶段执行。

入口只校验一次，拒绝重复判空和滥用try/catch；单次逻辑不乱抽函数，低概率防御先征求同意。
